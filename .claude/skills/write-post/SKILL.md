# 블로그 글 쓰기

원고는 `content/`(별도 비공개 저장소, 이 저장소에서는 무시됨)에 있고, 레이아웃은 이 저장소에 있다.
도구는 `.claude/skills/write-post/post.py` 하나. 경로는 저장소 루트 기준. Hugo는 `~/.local/hugo/hugo`(다른 위치면 `HUGO=` 환경 변수).

## 순서

```bash
git -C content pull --ff-only          # 관리 화면에서 생긴 커밋을 먼저 받는다
python3 .claude/skills/write-post/post.py new <slug> --title "제목" --category Gradle --tags "A,B" --date 2026-07-25
# content/blog/<slug>.md 를 아래 규칙대로 채운다
python3 .claude/skills/write-post/post.py check <slug>     # 규칙·식별어·링크 검사 + 초안 포함 빌드
python3 .claude/skills/write-post/post.py preview          # http://localhost:1313/ (초안·미래 날짜 포함)
python3 .claude/skills/write-post/post.py shot <slug> --height 5200        # PNG 경로 출력 → Read로 본다
python3 .claude/skills/write-post/post.py shot <slug> --dark --height 1400
# 다 쓰면 humanize-korean 스킬을 heavy(--strict)로 돌려 아래 "문장 다듬기" 규칙을 검사한다
git -C content add -A && git -C content commit -m "초안: <slug>"           # push는 사용자에게 맡긴다
```

`check`는 문제가 있으면 종료 코드 1. `preview`는 뒤에서 돌고 `kill $(lsof -ti:1313)`로 끈다.
공개는 lim-host 관리 화면(Tailscale)에서 사용자가 누른다. 초안(`draft: true`)은 사이트에 나오지 않는다.

## 글 규칙 (사용자가 여러 번 지적해 확정된 것, 2026-11 구조 규칙 개정)

본보기: 구조가 서로 다른 세 편을 읽는다. `content/blog/pulsar-tableview-message-mapper.md`(API 참고 글), `content/blog/document-search-58s-to-under-2s.md`(원인 추적), `content/blog/omp-model-roles.md`(비교·정리). 모든 글을 같은 뼈대로 쓰지 않는다. 2026-11 검토에서 글 103편이 "상황 → 이 글에서는 → ## 5~6개 → 마치며" 한 틀이라 문장을 다듬어도 AI가 쓴 글처럼 읽혔다.

- 구성: 겪은 상황 2~4문장으로 시작한다. 그 뒤는 글에 맞춘다. 원인 추적이면 증상 → 원인 → 고친 것, 설명 글이면 개념 → 예제 → 함정처럼 내용이 정한다. 부제·요약 문장·"코드로 보기" 링크 목록·상투적 마무리 금지.
- 도입의 "이 글에서는 …를 적습니다": 선택. 바로 아래 `##` 목차를 되풀이하는 안내라면 쓰지 않는다.
- 끝맺음: `## 마치며`는 선택. 겪은 일에서 나온 소감이나 그 뒤에 바뀐 습관이 있을 때만 쓴다("그 뒤로는 결과를 말하기 전에 지금 어느 커밋인지부터 봅니다"). 없으면 마지막 확인이나 `## 남은 것`으로 끝내도 된다. "~다는 것을 배웠습니다" 한 줄 일반론과 앞 내용 요약은 쓰지 않는다.
- `##` 나누기: 글에 필요한 만큼 3~7개. 정해진 순서는 없다. 이 글에만 있는 대상은 명사구("mapper가 불리는 때"), 판단이나 반전은 문장("처음 잰 \"벡터 2분\"은 측정 실수였습니다")으로 쓴다. 헤딩 바로 아래 첫 문장이 헤딩과 같은 말을 하면 그 문장을 지운다. `## 남은 것`, `## 직접 확인해 보기`는 실제로 할 말이 있을 때만 둔다.
- 제목: 구체적인 사실 하나(증상, 놀란 점, 숫자 중 하나)를 담는다. 30자 안팎, 40자를 넘기지 않는다. "~기록", "~하기"로 끝내지 않는다. 질문형은 독자가 실제로 검색할 질문일 때만 쓴다("JWT typ은 왜 …까"처럼 주제만 묻는 질문은 쓰지 않는다).
  - "가끔만 실패하는 테스트는 왜 생길까" → "CI에서만 실패하던 테스트, ack보다 되감기가 먼저 도착했다"
  - "JWT의 typ 값은 왜 대소문자를 가리면 안 될까" → "at+jwt는 통과하고 AT+JWT는 거부되던 이유"
  - "Pulsar 토픽 로드 시간 summary를 … 락으로 막은 기록"(60자) → "Summary.clear()가 observe() 기록을 버리던 틈"
- 강조 인용문 `>`: 쓰지 않는 것이 기본. 앞 문단에 없던 내용일 때만 한 번 쓴다. 바로 앞 문단을 한 줄로 되풀이하는 격언은 쓰지 않는다.
- 기초 설명: 독자가 이미 아는 개념(JWT 구조, try-with-resources 등)은 이 글의 문제와 닿는 부분만 한두 문장으로 쓴다.
- 쓰지 않는 문장: "고친 것은 작습니다/조건 하나입니다" 같은 겸손 공식, "먼저 배경부터 적겠습니다", "뒤에서 다시 나옵니다", "여기까지는 …입니다" 같은 진행 안내.
- 이어지는 글: 같은 사건이나 같은 주제의 글은 하나로 합칠 수 있으면 합친다. 질문이 서로 달라 따로 두면 배경은 첫 글에만 자세히 쓰고, 나머지는 한두 문장과 링크로 줄인다. 앞뒤 글끼리 본문에서 서로 링크한다.
- 말투: 1인칭, 짧은 문장, 겪은 일만. 제품·기술 이름은 영어 그대로(Gradle, WSL, JWT, thread). 억지 번역 금지("빌드 도구"). 일반 개념어는 쉬운 한국어("가끔 실패하는 테스트"는 flaky test보다 이것을 택함). 애매하면 바꾸기 전에 묻는다.
- `description`: 무엇에 관한 글인지 사실만 짧게. "~풀어 봅니다/~이야기입니다" 금지. 글 화면에는 안 나오고 목록·검색용.
- `date`: 작업(기여 반영)일 + 7~14일. 미래면 그날 전엔 사이트에 안 나온다(자동 배포가 매일 00:10에 돈다).
- `categories`: 기술 이름 하나. `tags`: 2~4개. 실명·회사명은 사이트 어디에도 안 쓴다(글쓴이 표시 없음).
- 링크: issue·PR·문서는 언급하는 그 자리에 하이퍼링크. gh나 curl로 실제 있는 주소만. public 저장소 코드 링크는 커밋 해시 기준.
- 회사 소재: `content/.private/forbidden-terms.txt`의 표현을 전부 뺀다("운영 중인 웹 서비스", "동료"). 업무 코드·캡처·경로 대신 재현 예제를 새로 쓴다. `check`가 이 목록으로 검사한다.
- 사실만: 참고 문서·코드에 있는 것만. 불확실하면 문장 뒤에 `<!-- 확인 필요: 이유 -->`(검토 후 지운다).

## 문장 다듬기 (2026-11 humanize-korean으로 글 237편을 다듬으며 정한 것)

아래는 그때 진단에서 가장 자주 지적된 순서다. 처음 쓸 때부터 피한다. 예시는 실제로 고친 문장이다.

- 연결어미 뒤 쉼표(237편 중 215편): "-고," "-며," "-지만," "-는데," "-면," 뒤에 습관처럼 쉼표를 찍지 않는다. 짧은 문장은 쉼표 없이 잇고, 절이 셋 넘게 이어지면 쉼표 대신 문장을 나눈다. 쉼표는 잘못 읽힐 때만 둔다("있는지 묻고, 없다면"). 제목 속 나열 쉼표("빌리고, 사용하고, 반납합니다")는 둔다.
  - "1.6이 나온 지 여러 해가 지났고, Gradle 안의 다른 코드도 … 알아보고 있어서, 변수가 있으면 …" → "1.6이 나온 지 여러 해가 지났습니다. Gradle 안의 다른 코드도 …"
- 긴 관형절(146편): 명사 앞에 꾸미는 말을 세 겹 넘게 쌓지 않는다. 앞부분을 서술어로 빼서 문장을 나눈다.
- 대칭 대구(134편): "A가 아니라 B입니다", "~것은 아닙니다", "X는 하나, Y는 …"를 한 글에 여러 번 쓰지 않는다.
  - "보낸 글자가 전부 화면에 찍히는 것은 아닙니다" → "보낸 글자가 전부 화면에 찍히지는 않습니다"
- "~기 때문입니다" 꼬리(56편): 이유를 매번 따로 떼어 "~기 때문입니다"로 끝내지 않는다. 원인을 먼저 쓰고 "그래서"로 잇거나 "-어서"로 붙인다.
  - "먼저 … 그대로 저장해 봤습니다. 화면에는 보이지 않는 신호라서 눈으로는 확인할 수 없기 때문입니다." → "화면에 보이지 않는 신호는 눈으로 확인할 수 없습니다. 그래서 먼저 … 저장해 봤습니다."
- 같은 길이·같은 끝맺음 반복(51편): 짧은 문장만 늘어놓지도, 긴 문장만 잇지도 않는다. 문단마다 "~습니다. ~습니다. ~습니다."가 같은 박자로 가지 않게 한다.
- 결말(51편): "~다는 것을 배웠습니다"로 어느 글에나 붙는 일반론을 쓰지 않는다. 이 글에서 겪은 일에 묶어서 쓴다. 다만 겪지 않은 교훈을 새로 지어내지 않는다.
- 분열문·결산 표지(48편+16편): "시간이 더 든 쪽은 확인하는 일이었습니다" → "확인하는 데 시간이 더 들었습니다". 문단 첫머리 "정리하면", "결국"은 뺀다.
- 헤딩 다음 첫 문장(37편): 헤딩을 그대로 되풀이하는 첫 문장을 쓰지 않는다.
- 사물을 사람처럼(34편): "updater가 믿는 것은 서명 하나입니다" → "updater가 확인하는 것은 서명 하나입니다". 실제로 일어나는 일을 쓴다.
- "그 N" 반복(25편)과 영어식 표현(18편): "그 thread", "그 값"을 잇달아 쓰지 않는다. "일꾼(thread)"처럼 풀어 쓰지 말고 그냥 thread라고 쓴다. 동사를 바꿀 때는 기술 의미부터 확인한다. 요청을 "만드는" 것(메시지 구성, CSRF에서 요청을 꾸미는 쪽)과 "보내는" 것(전송)은 다른 동작이라 서로 바꿔 쓰지 않는다.
- 검사할 때 지킬 것: 코드 블록·표·그림은 윤문 대상에서 빼고 돌린다. 합니다체, 1인칭, 링크·인라인 코드·숫자는 보존 지침으로 넘긴다. 윤문본이 원문에 없던 문장을 넣었는지는 원문과 대조해서 본다(2026-11 작업에서 실제로 나왔다). 구조 변경(합치기, 헤딩 정리)을 먼저 끝내고 윤문은 마지막에 한 번만 돌린다.

## 코드 블록 문법 (`layouts/_markup/render-codeblock.html`)

- 설명은 코드 안 주석(`//` 한 줄, 길면 `/* */`). 줄 옆 설명 `//>`은 거부됨. 줄은 90자 안에서 끊는다.
- 실제 저장소 코드: ` ```java {file="X.java" link="https://github.com/o/r/blob/<해시>/p#L10-L20" label="10~20행"} ` → 파일 이름 머리줄.
- 바뀐 부분: 속성에 `diff=true`, 각 줄 첫 글자 `+`/`-`/빈칸, 둘째 글자 빈칸.
- 본문 폭에 맞춰 접히므로 스크롤은 없다.

## 함정

- `date`가 미래인 글은 `hugo -D`로도 안 나온다. `check`·`preview`는 `-F`를 붙여 보이게 한다.
- 어두운 화면에서 코드 구두점이 안 보이면 `assets/css/syntax.css` 끝의 dark `.p/.o/.w` 규칙이 지워진 것.
- 관리 화면(lim-host)이 `content`에 커밋을 만든다. 작업 전 `pull` 없이 커밋하면 push가 거부된다.
- `content/.private/`는 Hugo가 빌드에서 뺀다(점으로 시작). 식별어 목록은 여기에만 둔다(공개 저장소 금지).

```bash
python3 .claude/skills/write-post/diagram.py      # 파일 안의 예제 6장을 content/blog/img/ 에 생성
```
